## Build and test

Needs Python 3 with numpy and Pillow; gcc for the emulator (`tools/mbee.py`
compiles `tools/emu/*.c` into `libmbee.so` on first use: Linux, macOS or WSL;
native Windows would need the loader changed to build a .dll).

```
python3 tools/fixjr.py         # build everything into build/ (turns out-of-range JRs into JPs and rebuilds)
python3 tools/bench.py         # fixed course over stages 0, 5, 13, 17: frames a second (compare builds with this)
python3 tools/alltest.py DIR   # every stage, six places each, every boss beaten by script; screenshots to DIR
python3 tools/alltest.py DIR 0 4 7   # just some stages
python3 tools/prof2.py 0 230   # where a frame's T-states go, by routine (stage 0, 230 frames)
python3 tools/run.py DIR       # title screen and a few shots
```

`tools/tour.py` has `Bot(stage=n, mono=False)`: `b.go(keys, frames)`,
`b.shot(png)`, `b.warp(tx, ty)`, `b.v('name', size)`; `b.pp` is the emulator
(`peek`, `peekw`, `watch(pc)` + `events()` for timelines, `prof()` /
`prof_map()` for per-PC T-state profiles). A watch on an address below 8000h
can hit code in any lower-window block: use upper (engine) addresses or a
map-block jump-table entry (0, 3, 6, 9...) to tell frames apart.

Always check a screenshot after an engine change: several bugs this project
had (blank soil rows, garbage sprites) only showed in pictures.

## Layout

- `src/engine.asm` (upper 32K, 8000h): start-up, stage load, the frame
  (`e_frame`, `e_present`), sprites (`sprite`, `spr_draw`, `getbuf`, `blast`),
  `e_upload`, `qdb_load`, input, `vpoll`.
- `src/map.asm` (block 5, lower window, entered by the jump table at 0): the
  quad engine: scroll steps, `col_draw` / `row_draw` / `m_cell`, slots,
  recolour pass (`m_mixed`), `m_present` / `m_show`, status line, `m_snap`.
- `src/game.asm` + `src/logic.asm` (block 4): front end, camera, HUD, Bix and
  the enemies (`logic.asm` is generated from the VZ source by `tools/port.py`).
- `src/hw.inc`: memory map and constants. `src/vars.inc`: upper variables.
  `gen.inc`, `stgtab.inc`, `engsym.inc`, `tunes.inc`, `sprtab.inc`,
  `loadfiles.inc`, `proglen.inc` are generated by `tools/build.py`.
- `tools/data.py`: the 20 stages from the VZ level files in `tools/vz/`
  (`level1`, `levels2`, `levels3` = Lost Levels); `tall()` turns a 12-tile VZ
  level into 16 tiles. `tools/night.py`: night tiles, sky painting, quads,
  stage blobs. `tools/font.py`: the bold font and HUD glyphs.
- RAM blocks: 4 game, 5 map code and tables, 7 the cell map, 6/21/22 the quad
  picture cache, 8-15 stages, 16-20 sprites. Only blocks 4..22 may be written
  while CP/M is alive (loader).

## How the engine works (short)

- Screen: 40x25 of 8x10 cells (320x250, PAL, 312 lines). Row 0 status line,
  24 playfield rows. No interrupts: the vertical blanking is polled
  (`vpoll`; `mpoll` in map loops also uploads slots when the middle blanking
  is seen). Video RAM can only be written in blanking: the 6545 holds the CPU
  to the end of the line otherwise (the emulator models this; it is what
  makes overruns so costly).
- Quads: each screen cell shows a 2x2 block of world cell glyphs at one of 12
  offsets (4 across x 3 down: 0/3/7 lines) = PCG bank 0-11. 127 slots
  (codes 80h+slot) with refcounts and a free ring (each slot in it at most
  once: bit 0 of M_SLFL). A fine scroll step = PUSH-fill of 960 attribute
  bytes; a coarse step = start address + one new column/row.
- Slot pictures live in the record cache (blocks 6/21/22, 136-byte records);
  `qdb_load` only notes where (SLRA/SLRB at EE00h/EF00h); `e_upload` sends
  them to the PCG straight from there; sprites read backgrounds from there too.
- Cells whose ink differs between offsets are in per-column bitmaps
  (M_COLMIX across, M_VMIX down); `m_mixed` recolours only cells whose ink
  really changes.
- Sprites: a private glyph per touched cell, two PCG pools (banks 14/15)
  taking turns, buffers 16 bytes at C000h, CELLMAP indexed by ring offset
  (D000h, 2K).
- A frame is 2 fields: logic, `e_frame` (scroll, queue, recolour, sprites,
  restores, `M_PRESENT`: uploads/blast in the middle blanking if in time),
  `e_present` (`M_SHOW`: start address, status line, fill, colour flips,
  cell flips in the second blanking).

## Where it stands (Nov 2026)

- 20 Lost Levels stages + 5 bosses play through by script. Emulator speed:
  levels 22.9-24.2 fps, bosses 24.8-25 (`alltest.py`); bench 22.87.
- Slowest frames: vertical pans (a row of 40 cells + recolouring the
  two-ink cells as the offset moves down), and many new quads at once.
- Sprite cell: about 1,600 T to build, plus restore and PCG write.
- Not yet tested on the real machine since the 8x10 PAL screen and the speed
  work: the owner was about to test. Ask what they found before more engine work.

## Next, as discussed

1. Real-machine test results first (picture stability on PAL 312 lines,
   smoothness, sprites over scenery, sound, keys).
2. Option 1, which the owner leans towards: genuinely taller levels (e.g. 24
   tiles). The engine caps level height at 16 tiles (32 cell rows): the cell
   map, M_COLMIX/M_VMIX (4 bytes a column), `mx_masks` and `rowoff` all
   assume 32 rows. Then give each level an upper route (logs, ledges, star
   trails) and deeper caverns below, in each world's style, so the camera
   has reason to scroll. Keep the 116-quads-a-screen budget.
3. Still missing: logs and lifts move a whole cell at a time
   (`m_platcells` is a stub), particles, level clock, title picture,
